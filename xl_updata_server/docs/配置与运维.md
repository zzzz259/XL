# Update Server 配置与运维

配置模式定义于 `server_app/config.py`，样例默认值见 `config.toml.example`。部署用的 `config.toml` 含密钥和路径，不提交。

## 配置项

| TOML | 用途 | 示例默认值/约束 |
|---|---|---|
| `[server].environment` | 服务器环境隔离策略 | `main` 或 `test`；旧配置缺失时默认为 `main` |
| `[server].timezone` | 调度时区 | `Asia/Shanghai` |
| `[server].normal_interval_seconds` | 常规轮询间隔 | `3600`，必须为正数 |
| `[server].burst_interval_seconds` | 密集模式间隔 | `60` |
| `[server].burst_duration_seconds` | 密集模式最长时间 | `1200` |
| `[server].burst_anchor` | 固定密集周期锚点 | 必须使用带时区偏移的 ISO datetime，例如 `2026-10-09T10:00:00+08:00`；之后每 21 天计算一轮，服务重启不会改变锚点。不要使用 `last_friday` 或 `auto` |
| `[polling].enabled` | CDN 定时检查开关 | `main` 默认 `true`；`test` 环境无条件强制为 false，不能用此开关覆盖 |
| `[api].enabled/host/port/token_env` | 本机手动控制接口 | loopback 地址；生产默认 `127.0.0.1:8790`、test 为 `127.0.0.1:8791`；Bearer token 从 systemd 环境变量读取，不写入 TOML |
| `[paths].data_dir` | 持久数据目录 | 相对配置文件目录解析，默认 `data` |
| `[paths].java_bin` | Java 可执行文件 | 默认 `java`，可配置绝对路径 |
| `[paths].unluac_jar`、`unluac_opmap` | Lua 反编译器和 opcode map | 样例指向相邻 `xl_updata_tool/tools/lua/` |
| `[paths].node_bin` | Node 可执行文件 | 默认 `node`；renderer 要求 Node 20+ |
| `[paths].character_card_font` | 可选 CJK 字体 | 空值时使用 renderer 系统字体搜索 |
| `[cdn].base`、`categories` | CDN 地址和下载类别 | 当前只支持 `Arts`、`Data` |
| `[cards].enabled` | 是否渲染图鉴卡片 | 默认 `true`；关闭时只处理角色数据 |
| `[rerun_schedule].enabled` | 是否生成普通首次复刻排期 | 默认 `true`；排期解析/渲染故障不阻断角色数据更新 |
| `[rerun_schedule].refresh_seconds` | 无新游戏包时的重渲间隔 | 默认 `3600` 秒；轮询器每分钟检查周期边界，遇到边界立即重渲 |
| `[rerun_schedule].forecast_limit` | PNG 展示行数上限 | 默认 `20`；完整队列/JSON 不截断 |
| `[rerun_schedule.anchor]` | 用户确认的当前期锚点 | 默认罗蕾娜 `10000223` / 雪莉 `10000212`，`2026-09-22 10:00` 至 `2026-10-13 05:00`（`+08:00`）；结束时刻单独按每期 21 天平移 |
| `[security].assetbundle_key` | 资源处理密钥 | 必须为 16 个 UTF-8 字节；生产配置不得公开 |

改完配置先使用 `run_server.py --once` 做单次验证。修改周期锚点时检查目标时区和首次检查时间，避免意外密集轮询。

### test/main 环境隔离与控制 API

阿里云部署的生产目录为 `/home/admin/xl_updata_server`，test 目录为
`/home/admin/xl_updata_server-test`。两份配置分别使用 `environment = "main"`
和 `environment = "test"`，并配置不同的 `data_dir`；后者包含独立的
`state.sqlite`、下载、版本、角色产物、outbox 与排期快照。`xl_deploy` 的
`test_backend_config`、`test_backend_data` 必须与生产路径不同，且都在
immutable release 目录之外。

test 服务常驻，但**不自动轮询 CDN**。即使配置写成 `[polling].enabled = true`，
test 环境仍强制禁用定时拉取；GitHub 自动部署只更新代码，不触发一次游戏处理。
需要按需验证时，通过 `127.0.0.1:8791` 调用手动接口；生产接口在 `127.0.0.1:8790`。
两者只绑定 loopback，不应开放端口。

| 方法 | 路径 | 说明 |
|---|---|---|
| `GET` | `/healthz` | 无认证只读健康状态，不读 CDN、不写数据 |
| `GET` | `/api/v1/status` | Bearer 认证；显示环境、轮询策略、活动任务和持久化的最近一次运行摘要 |
| `POST` | `/api/v1/updates/run-once` | Bearer 认证，空 body；排队一次正常检查与处理，返回 `202` 和 job ID |
| `GET` | `/api/v1/jobs/{job_id}` | Bearer 认证，读取持久化任务状态/结果 |

test 与 main 的 API 密钥分别放在 mode-600 的
`/home/admin/.config/xl_updata_server-test/api.env` 和
`/home/admin/.config/xl_updata_server/api.env` 中，变量名为
`XL_UPDATE_API_TOKEN`，每个至少 32 个非空白字符且必须不同。不要把 token
放入仓库、命令行参数或日志。两个环境共用单飞协调器规则：已有定时或手动任务时
第二次手动请求返回 `409`；服务停止时返回 `503`。系统关闭时停止接收新任务，等待进行中的更新完成。

本机运维示例（先从安全凭据管理器读取 token 到环境变量，避免明文回显）：

```bash
curl -H "Authorization: Bearer $XL_UPDATE_API_TOKEN" \
  -X POST http://127.0.0.1:8791/api/v1/updates/run-once
curl -H "Authorization: Bearer $XL_UPDATE_API_TOKEN" \
  http://127.0.0.1:8791/api/v1/status
```

`run_server.py --healthcheck --config ... --expect-environment test` 是只读检查，
会验证配置声明的环境、持久化数据库只读可开、解码器/Java/渲染依赖可用，不连接 CDN。

## 安装依赖

目标服务器安装 Python 3.11/3.12、Java 21。创建服务端自己的 venv 并安装 Python 依赖：

```bash
cd /home/admin/xl_updata_server
bash scripts/install_server.sh
bash scripts/install_renderer.sh
```

renderer 还需要 Node 20+、Cairo/Pango/JPEG/GIF 系统库与 node-canvas。`scripts/install_renderer.sh` 会调用 `dnf` 并运行 npm 安装，需 root/sudo 且会更改系统软件包；执行前确认发行版仓库的 Node 版本满足 `renderer/package.json`。渲染 Node 进程的堆上限为 512 MB，以控制低配服务器的内存使用。

使用 `xl_deploy` 不可变 release 部署时，候选版本预检会在 release 自己的 `renderer/` 下安装 npm 运行依赖并执行 `require('canvas')` 检查；检查失败会在停服/切换前中止。systemd 的 `NODE_PATH` 只作为共享运行时兜底，不代替候选 release 的依赖预检。

```bash
bash scripts/check_server.sh
.venv/bin/python -m unittest discover -s tests -p '*_unittest.py' -v
```

`check_server.sh` 检查配置、unluac、Python 模块、Node renderer、Java 和 Python 源码编译；它不能证明远端 CDN 或真实长图渲染结果正确。

## systemd 运行

`xl_deploy/deploy/` 提供 production 与 test 两个 unit，并用 `xl-updata.slice`
将两个后端的合计 CPU 限制在一个核以内；各 unit 本身还设 `CPUQuota=100%`。
后端服务均为 `Type=simple`，API 与 daemon 在同一进程内。test 的
`xl-updata-server-test.service` 使用 `current/test`、独立 venv/配置/数据和
独立 API 环境文件。正式服务仍使用 `current/main`。部署控制器在切换前执行只读
环境健康检查，重启后检查各自 loopback `/healthz`。

```bash
systemctl --user status xl-updata-server.service xl-updata-server-test.service
journalctl --user -u xl-updata-server.service -f
```

用户服务要在 SSH 注销后继续运行，需由管理员为该用户启用 linger。两个 backend unit 设置 `Restart=on-failure`、`Nice=10`、`CPUQuota=100%`、`MemoryHigh=700M`、`MemoryMax=1G`、`TimeoutStopSec=300`；父 slice 限制 backend 合计 CPU 预算为 100%。部署器更新 test 时不会停止生产 server 或共享 router。

`scripts/run_full_production.sh` 提供独立目录的一次性低并发验证，不移动正式服务 current 指针。按脚本输出和生成的 manifest 检查；不要用 shell 后台化或 `nohup` 代替 systemd 管理。

```bash
./scripts/run_full_production.sh
systemctl --user status xl-updata-full-production
journalctl --user -u xl-updata-full-production --no-pager
```

该脚本的报告写在 `data/full-production-<时间>/`，检查 `manifest.json` 中的数据、皮肤、长图成功/警告/失败统计。它不会改动 `data/current_version.json`。

## 数据和保留

```text
data/
├── state.sqlite
├── current_version.json
├── rerun_schedule/current.json
├── rerun_schedule/current.png
├── rerun_schedule/snapshots/<快照ID>/{current.json,current.png}
├── catalogs/
├── versions/<版本>/{rerun_schedule/,character_data/,character_cards/}
└── outbox/<版本>/
```

`versions/<版本>/` 保存版本化角色数据、卡片和 manifest；正常运行不会自动删除已发布历史版本。首次启动只建立基线，不向 outbox 放入全量历史图。Bot 成功分发某版本的整批图片后清理对应 outbox；失败时保留以供重试。

后续版本会比较同一角色 ID 的规范化 JSON 全字段：信息有变化就重渲角色图鉴卡，并在 manifest 记录 `updated_characters_count`；变化角色不会进入 Bot outbox，只有新增角色才分发到群。

### 普通首次复刻排期

处理游戏版本时，服务从 Lua 白名单提取 `BaseGacha` 与 `BaseGachaBottomUp`，只按 `type=2` 池审计。`bottom_main_type=1 && bottom_type=201` 为普通池；`bottom_main_type=2 && bottom_type=301` 为特殊池；其它组合、缺少外键或普通池多主 UP 都会保留诊断且不进入预测。历史顺序按数值 `sort`，再按 Gacha ID 稳定排序；限定池不改变普通 FIFO。

排期仅预测“首次普通复刻”。普通首发加入队尾；首次复刻从队列移除实际角色，插队会生成异常记录；后续复刻不重复影响队列。卡池已在 Lua 出现不表示官方已经开放。默认锚点按 `Asia/Shanghai` 计算，开始与结束分别加 `21*n` 天；每期 05:00 结束至 10:00 开始之间明确显示为空档。锚点后的期次及典藏标记均标为预计。

遇到 Lua 配置与已核对事实不一致时，可在 `[rerun_schedule]` 下添加 `[[rerun_schedule.overrides]]`，按唯一 `gacha_id` 精确纠偏；每项必须填写可审计的 `source`，可选覆盖 `pool_kind`、`character_id`，或用 `exclude_from_prediction = true` 保留历史记录但不进入预测。覆盖结果及来源会进入异常审计信息。不要按角色名或文件名做全局替换；没有证据的池继续标为 unknown 并排除预测。

每个版本目录先完整写入同版 JSON/PNG 不可变快照，再由版本指针发布；Bot 通过 `source_version` 和 PNG SHA-256 校验读取。解析/字体/渲染失败不会覆盖旧成品；新版本缺少排期时继承 last-known-good，并由 Bot 提示数据版本已过期。服务每分钟检查时钟边界，并按 `refresh_seconds` 重渲已有队列，不重新下载或反编译 Lua。排期数据保留在版本目录和稳定镜像，不随 outbox 清理。

历史报告给出的 85/69/16 等计数及截至 `24000087` 的 11 人队列由标准库回归样例覆盖。本地没有任务书提及的完整 Lua ZIP，因此这些用例验证算法与报告基线，不代表重新解析该 ZIP 完成了真实数据审计。

## 与 QQ bot 的交接

Bot 的 `[watch].outbox_dir` 指向服务端 `data/outbox`；`character_data` 和 `versions_dir` 指向本服务输出。双方通常位于同一主机/用户下，通过共享文件系统交接；服务端没有对 bot 的 HTTP API。

Manifest 包含版本、生成时间以及角色 `{id, name, file_name}` 列表。修改字段或清理时机时，必须同时更新 `xl_qqbot` 说明和双方契约测试。

## 故障定位

- `systemctl --user status ...` / `journalctl --user -u ...`：启动与调度错误。
- `run_server.py --once`：单次执行结果及失败阶段。
- `data/versions/<版本>/manifest.json`：Lua 解析、角色统计、卡片成功/警告/失败和下载摘要。
- renderer 错误：核实 `node --version`、`renderer/node_modules`、Cairo/Pango 和字体；Python 测试不能代替真实渲染。
- Lua 解码错误：核对 Java 21、unluac 和 opcode map 是否匹配。

日志和 manifest 可能含个人路径或资源名，对外分享前先脱敏。

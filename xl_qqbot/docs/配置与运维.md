# QQ Bot 配置与运维

配置解析在 `bot_app/config.py`，字段默认值见 `config.toml.example`。Bot 凭据、SESSDATA、目标群信息和服务器路径均属部署配置；本地 `config.toml` 不得提交。

## 配置字段

### QQ 与 outbox

| TOML | 作用 |
|---|---|
| `[bot].appid` / `secret` | QQ 开放平台机器人凭据，必填 |
| `[bot].openid` | 可选机器人群内 openid，用于识别提及 |
| `[watch].outbox_dir` | 服务端 `data/outbox` 路径，必填 |
| `[watch].interval_seconds` | outbox 轮询秒数，默认 30，至少 1 |
| `[watch].data_dir` | Bot 持久状态目录 |
| `[watch].character_data` | 服务端当前角色数据 JSON 路径 |
| `[watch].versions_dir` | 服务端版本数据目录 |
| `[target].group_openids` | 可选固定发送群列表；空数组时使用从 Gateway 事件学到的群 |
| `[target].auto_learn_from_events` | 是否记录加群/群消息事件中的群 ID，默认开启 |
| `[upload].file_base_url` | 可选图片公网 URL 前缀；使用前需确保 URL 可访问且路径映射正确 |
| `[message].template` | 可选文字模板，支持 `{version}`、`{name}`、`{file_name}` |

QQ 平台不提供机器人当前所在群的通用群列表接口；自动学习依赖加群和群消息事件。不要把群 openid 写进公开文档或日志。

### 群与功能权限

- `[groups].debug` / `[groups].test`：调试/测试群 openid 数组；未列出的群默认为 `production`。
- `[features]`：功能最低开放级别；合法值 `production`、`test`、`debug`。级别具有累积关系：production 群只用 production 功能，test 群可用 test 和 production，debug 群可用全部。
- 当前 feature key：`character_query`、`character_push`、`update_notice`、`bilibili_watch`、`rerun_schedule_query`。排期查询缺省为 `debug`（其他未配置项默认 production）；非法级别启动时报错。
- 事件查询在权限外静默忽略；推送会按群级过滤。分级由 router 和 service 共同执行。

### 复刻排期查询

在明确 @机器人的群消息中，`复刻`、`复刻表`、`复刻排期`、`下次复刻`、`卡池复刻`、`复刻时间`、`下一期谁复刻`，以及“某角色什么时候复刻”会在角色名模糊匹配前进入排期查询。普通聊天中的泛化“复刻”文本不会触发。新配置默认只在 debug 群开放；确认后可在 `[features]` 将 `rerun_schedule_query` 提升到 `test` 或 `production`。

Bot 从服务端当前版本目录读取不可变 PNG，并核对 JSON 指向、路径 containment 和 SHA-256。若成品版本落后于当前游戏版本，会随图提示缓存版本。此命令强制使用本地分片上传，不使用以 outbox 为根的 URL 映射，也不把文件放进 watcher outbox。真实 QQ 凭据、媒体上传和群端展示仍须在授权测试群现场验证。

### Router 与 Bilibili

- `[router]`：`test_port=8782`、`production_port=8783`、`forward_timeout=8` 秒。现有 router 保留群的原始 debug/test/production tier；debug 和 test 都转发到 test worker，production 转发到正式 worker。`debug_port=8781` 只为旧配置兼容保留，新部署不启动 debug worker。服务监听 `127.0.0.1`，不要把内部 HTTP 端口直接暴露到公网。test worker 配置必须保留 `[groups].debug` 和 `[groups].test` 两组原有群 ID及其 feature-level 设置，以便 worker 再计算权限时不丢失 debug 门禁。
- `[bilibili].enabled`：是否启用监视，默认开启；`interval_seconds` 默认 300。
- 定时密集检测字段：`burst_times` 默认 `['10:00', '17:00']`，按 `timezone`（默认 `Asia/Shanghai`）解释；每个时刻起持续 `burst_window_seconds`（默认 300 秒），期间按 `burst_interval_seconds`（默认 60 秒）轮询。窗口支持跨零点；设为 `burst_times = []` 时只使用常规间隔。
- `[bilibili].sessdata`：启用监视时需要有效登录 Cookie；妥善保存在本地配置中，不能发给他人。
- 每个 `[[bilibili.targets]]` 含唯一数字 `mid`、可选显示名 `name` 和 `mode`：`full` 为图文详情/原图加视频通知，`notice` 只发一行通知。建议先以 notice 模式验证群路由。

监视状态保存在 `[watch].data_dir/bilibili_state.json`，每个 UP 主分别记录动态和视频基线；首次观察以最新条目建立基线，不补发历史内容。旧版单目标状态会迁移到默认目标。每个目标的动态和视频每轮各最多处理 5 条，未处理项留到下一轮；单路请求失败不会阻断其他目标。密集检测时间表可用于新动态常见时段缩短轮询间隔。

## 本地测试

```bash
cd xl_qqbot
python3.11 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
cp config.toml.example config.toml
.venv/bin/python -m unittest discover -s tests -p '*_unittest.py' -v
```

默认测试使用 mock，不需要也不会验证真实平台凭据和网络链路。配置校验可通过单测或应用启动验证；真实发送需单独使用授权测试群并遵守平台限制。

## 分支自动部署（新部署流程）

新版本使用仓库内 `xl_deploy/` 控制器和 systemd **user** units（由 `admin`
运行，不用 `sudo`）。只读盘点、显式启用、恢复和凭据操作见
[部署控制器运维指南](../../xl_deploy/README.md)。旧 `deploy/` 与安装脚本属于
历史手动部署流程，不要与新流程混用，也不要让两个 router 同时登录同一 QQ
Gateway。

分支映射：`debug` → `xl-qqbot-debug.service`；`test` →
`xl-qqbot-test.service`；`main` → `xl-qqbot-prod.service`、router 和按变更范围
选择的更新服务。代码使用 `/home/admin/xl_deploy/releases/` 不可变版本，经过
`/home/admin/xl_deploy/current/{debug,test,main}` 独立切换。旧 bot/backend 配置、
持久状态和 `data/` 留在原路径，不复制进 release。

每分钟运行一次单次轮询；只有 GitHub Actions **XL CI 对相同分支及精确 SHA
成功**后才部署。Bot 更新先发“检测到更新，正在更新bot，期间将暂停服务”，再维护、
排空并停止受影响服务；切换后启动并通过健康检查，最后发“更新完毕”，之后才发送
非空的新版本公告。journal 驱动中断恢复/回滚。QQ 通知为 **at-least-once**，崩溃
窗口内可能重复发送，无法保证 exactly-once。

GitHub token 放外部 `~/.config/xl_deploy/secrets.env`，router bearer token 单独
放 `~/.config/xl_deploy/router.token`；两者权限必须 `600`，配置目录建议 `700`。
bot `config.toml` 含 QQ 凭据和 router token，backend 配置含生产 assetbundle key，
均留在原路径并设置 `chmod 600`，不可进仓库或日志。初始化默认
只盘点；显式 `--activate` 才安装 user units，且不覆盖已有 unit/config、不启停
服务、不迁移或删除旧目录。

## 旧版多进程部署（仅存量手动环境）

旧 `deploy/` 有 router、production、debug、test 四个 systemd user unit。以下命令只适用于尚未切换到 `xl_deploy` 的手动环境；不要对新 immutable release 布局执行这些旧安装命令。

```bash
mkdir -p ~/.config/systemd/user
cp deploy/xl-qqbot-router.service deploy/xl-qqbot-prod.service \
   deploy/xl-qqbot-debug.service deploy/xl-qqbot-test.service \
   ~/.config/systemd/user/
systemctl --user daemon-reload
systemctl --user enable --now xl-qqbot-prod xl-qqbot-test xl-qqbot-debug xl-qqbot-router
systemctl --user status xl-qqbot-router
journalctl --user -u xl-qqbot-router -f
```

停用单个服务：`systemctl --user disable --now <unit>`。部署脚本和 units 默认按 `/home/admin/xl_qqbot` 配置，不是任意路径安装器。`scripts/install_bot.sh` 安装的是旧的一体化兼容服务，不应与四进程拓扑同时接收同一个 QQ Gateway。

## 持久状态

`[watch].data_dir` 下保存 `learned_groups.json`、`aliases.json`、`learned_aliases.json`、`update_notice_state.json`、`bilibili_state.json`、分发状态和临时下载内容。备份前停服务或使用一致性快照；不要把该目录清空来“重置”单一功能，否则可能重复推送或丢失学习结果。

### outbox 消费契约

Bot 读取服务端 `data/outbox/<版本>/manifest.json` 及图像。每图每群的发送状态持久化；只有该版本所有目标图片成功，才移除对应 outbox 目录。进程重启后根据持久状态续发，避免重复完成项。服务端首次运行的基线不产生历史图推送。

## 日志与排障

systemd user service 默认写入 journald：

```bash
journalctl --user -u xl-qqbot-router --since today
journalctl --user -u xl-qqbot-debug --since today
journalctl --user -u xl-qqbot-test --since today
journalctl --user -u xl-qqbot-prod --since today
```

- Router 已连接但查询无响应：确认对应级别服务 unit 正常、回环端口正确，并检查 router 的 HTTP 转发错误。
- 事件未路由：检查群是否已学习/手动列入，检查 `[features]` 最低级别，以及服务端 `GET /health` 是否可访问。
- 图鉴分发失败：核对共享 outbox 路径、manifest 文件名、目标群和发送状态；失败项应留待下一轮重试。
- B 站 412/鉴权失败：核对 SESSDATA 是否过期、系统时间及网络可达性；勿把凭据写进日志。
- 图片上传：配置 `file_base_url` 时确保静态 URL 可从 QQ 平台访问。未配置时的 SDK 分片上传路径尚需真实凭据验证，不能仅以 mock 测试宣称可用。

修改 QQ API、outbox schema、状态文件或权限策略时，更新对应测试及[服务端交接文档](../../xl_updata_server/docs/配置与运维.md)。

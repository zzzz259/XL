# XL Update Tool 架构与协作基线

> 本文是稳定性与架构收口后的当前基线。它描述可依赖的边界、运行时目录契约和多人协作规则；代码与本文不一致时，先在 Issue 中说明，再同步修正文档。

## 1. 项目定位与演进原则

XL Update Tool 的主链路是：

```text
检查版本 → 计算 Bundle 差异 → 下载并校验 → 导入 AssetStudio → 分类导出 → 预览/角色/音频消费产物
```

项目当前采用 `bootstrap / platform / shared / features / ui shell` 的结构。日常改动遵循四条原则：

1. 先稳定契约，再修改实现；
2. 纯逻辑可以在无 Qt、无 GUI、无真实游戏资源的环境中测试；
3. 每个功能域保持可回退、可验证；
4. 共享文件改动小步提交，避免多人长期占用同一文件。

## 2. 当前边界（As-Is）

### `app/platform/` 与 Feature 基础能力

平台能力位于 `app/platform/`，角色 Lua 解析正式归属 `app/features/characters/parser/`；版本、音频、预览和导入领域实现分别位于对应 Feature。`app/core` 已从生产结构移除。

约束：

- 不得导入 `PySide6`、窗口、控件或信号；
- 不得直接操作 UI 状态；
- 外部工具调用应逐步收敛到 adapter/service 层；
- 新增公共函数优先提供类型注解和最小单元测试。

下载与 Bundle 能力位于 `app/platform/`，Qt 线程包装位于 Versions/Importer Feature；版本、角色、音频和预览领域实现已归入对应 Feature，角色 Lua 解析拆分为 `app/features/characters/parser/common.py`、`words.py`、`progression.py`、`skills.py`、`cards.py` 和 `assembler.py`。生产代码不再依赖 `app/core`。

### `app/ui/` 与 Shell

版本、音频、预览和角色页面分别由对应 Feature Page 自持控件、状态和语义信号；`MainWindow` 只负责窗口骨架、通用导航、Shell action、全局任务宿主和 Runtime 激活。
音频树节点构造和领域状态集中在 `app/features/audio/`；音频扫描、导出、增量快照、未读状态和专辑归属均由 Audio Feature 提供。
预览列表项、缩略图加载和导出编排集中在 Preview Feature；主窗口只接收通用任务状态。
版本下载目标计算集中在 `app/features/versions/version_download.py`；Qt 下载 worker 位于 `app/features/versions/download_worker.py`，只负责执行计划和回报进度。

Ruff 的强制门槛覆盖项目内全部 `app/`、`tests/` 和兼容入口；CI 从 `xl_updata_tool/` 目录执行。`MainWindow` 与旧版 `AssetBrowser` 的历史兼容代码必须保持边界，不得继续承载新领域逻辑。

Shell 负责 Qt 生命周期、信号槽、用户提示和页面显隐；领域行为由 Feature Runtime 和 `ApplicationShellContribution` 提供。UI 不得直接调用 Feature 内部实现、文件遍历、解析规则或导出策略。

旧版 `asset_browser.py` 目前仅通过 `app/ui/legacy/asset_browser_entry.py` 暴露兼容入口；主流程继续使用 `ImportASWorker`，后续可独立删除或维护旧窗口。

`main_window.py` 是稳定 Shell 入口。新增功能应进入对应 Feature；只有确需调整 Shell、Runtime 或共享契约时，才建立独立 Issue 并补充架构测试。

### `workers/`

负责耗时任务的 Qt 包装：线程生命周期、取消、进度信号和结果信号。耗时任务内部的纯计算应下沉到 platform/features，Worker 不应成为新的业务单体。

### `features/` 与 `adapters/`

- `features/`：当前承载部分领域流程和 UI 侧业务编排，例如导出分类、角色数据、FairyGUI 解析；其中导出控制器仍包含 Qt 弹窗、Worker 启动和外部工具协调，后续需拆成无 Qt 应用服务与 UI 适配器；
- `adapters/`：AssetStudio、SpineViewer、FFmpeg 等外部工具的命令构造、输出解析和兼容处理。

## 3. 运行时目录与输出契约

所有运行时路径通过 `app/platform/paths.py` 获取，避免在业务代码中重复拼接项目根路径。

| 区域 | 当前职责 | 长期规则 |
|---|---|---|
| `data/bundles/` | 原始下载 Bundle，按版本/哈希组织 | 下载产物只追加或替换临时文件后原子落盘 |
| `data/material/` | AssetStudio 中间导出，兼容旧流程 | 视为可重建缓存，不作为长期展示数据唯一来源 |
| `data/seeds/` | 版本分类 JSON 缓存 | 可重新拉取，缺失时自动恢复 |
| `data/xl_updata.db` | 版本和 Bundle 元数据 | 磁盘扫描结果用于校准，不盲信历史状态；版本变化的 `size_diff` 表示新旧 Bundle 的实际字节差 |
| `output/lua/` | 反编译后的 Lua 展示输入 | 角色解析只读这里 |
| `output/character_data/` | 角色结构化缓存 | 源文件变化时失效重建 |
| `output/character/`、`output/fgui/`、`output/audio/`、`output/video/` | 可消费的分类产物 | 失败任务不得用半成品覆盖已成功产物 |
| `logs/<session_id>/` | 启动级日志会话、错误日志和 Debug 诊断文件 | 文件日志不可用时仍保证控制台可诊断；Debug 环境摘要和崩溃报告与会话绑定 |

当前仍有部分预览/音频流程读取 `data/material/` 作为输入，这是兼容现实而不是理想边界。后续每迁移一个消费者，都必须同时保留旧路径回退或明确给出迁移提示，避免影响已有建设。

## 4. 输出状态模型（目标契约）

每个导出任务建议按以下状态推进：

```text
发现输入 → 写入临时目录 → 校验数量/格式 → 原子移动到 output → 写入完成标记
       ↘ 失败：保留旧产物，清理临时目录，记录可定位错误
```

最低要求：

- 单个文件失败不应让整批任务无故中止；外部工具部分失败但已有有效目标产物时应提交并记录警告；
- 任务取消后不能把未完成文件报告为成功；
- 进度必须区分“已跳过、已成功、失败、取消”；
- 增量任务按输入 hash/mtime 判断，不以“目录非空”作为全局完成条件；
- 文件名或相对路径冲突必须显式报告，不能静默覆盖。

## 5. 多人协作拆分策略

领域认领建议如下：

| 领域 | 主要目录 | 协作规则 |
|---|---|---|
| 版本/下载 | `features/versions/`、`platform/downloader.py` | 先保持信号兼容，再改数据模型 |
| 导入 AssetStudio | `ui/workers/import_as.py`、`ui/adapters/` | 任何输出目录改动必须同步契约文档 |
| 图片/Spine | `ui/features/`、`ui/adapters/spine_adapter.py` | 先抽纯路径/配对逻辑，再动 UI |
| 音频 | `features/audio/` | 自动后处理、临时清理、增量解密、分类和未读状态单独验收 |
| Lua/角色 | `features/characters/parser/`、`features/characters/` | 解析器保持无 Qt；按职责修改 parser 子模块，样例数据脱敏后再进测试 |
| 主窗口 | `ui/main_window.py` | 仅做协调；大改必须单独 Issue/PR |

推荐的 PR 粒度是“一个边界、一个可验证结果”，例如“下载 Qt 包装迁移”或“定义导出状态”，不要把 UI 美化、路径迁移和解析器重写放在同一 PR。

## 6. 分阶段路线

### 当前基线

- `app/core` 已退出生产结构；未登记的旧路径不得重新成为生产依赖。
- 五个 Feature 通过 `FeatureRuntime` 注册、激活和关闭；Shell 只消费通用 Runtime/contribution 契约。
- `app/platform`、`app/shared` 和 `app/bootstrap` 提供稳定的基础设施、共享 UI 和装配入口。
- pytest、Ruff、AST、import smoke、Qt offscreen smoke 和 diff check 是合并前固定门禁。

### 后续维护方向

- 下载、导入和导出继续使用临时目录、校验、原子发布和取消检查。
- 新增行为优先在 Feature 内完成，并为增量、取消、重试和冲突补充契约测试。
- 修改 Shell、Runtime、Platform 或 Shared 时，必须单独说明影响范围，避免多人同时编辑公共入口。
- 继续维护脱敏样例、回归资源清单、版本迁移说明和发布工具链。

## 7. 每次改动的验收清单

- 是否先有对应 Issue，且写明背景、边界和验收标准？
- 是否影响公共文件或输出目录契约？
- 是否有至少一个自动化测试或可复现的 smoke check？
- 是否运行 `pytest`、`ruff --no-cache`、全量 Python compile？
- 是否同步 README/开发文档/协作说明？
- 是否能在失败、取消、重复执行后恢复？
- 是否没有把密钥、真实账号、外部服务凭据或敏感资源写入仓库、Issue、PR、聊天和命令行参数？

# Findings & Decisions

## Requirements
- 用户希望整体重审 XL 桌面应用的界面美术与 UI，而不是只修一个页面。
- 新蓝灰主题可以保留，但需要去除 AI 味并提升完成度。
- 其他现有主题目前不满足审美要求，可评估移除、隐藏或重做。
- 优先保证已有功能、数据处理、启动流程和多人协作边界不受影响。
- 需要从整体视觉系统出发：主题、色彩、字体、间距、层级、组件、页面和交互反馈。

## Research Findings
- 当前仓库分支为 `chore/architecture-stabilization`，工作区在审计开始前干净且与远程同名分支同步。
- UI 入口和实现主要位于 `xl_updata_tool/app/ui/`，包含 `main_window.py`、`theme.py`、`panels.py`、`asset_browser.py`、`views/`、`dialogs/`、`widgets/`、`features/` 和 `legacy/`。
- 本次先建立视觉基线，不立即修改生产代码；具体问题需继续通过源码、主题字符串、页面结构和实际运行画面确认。
- `theme.py` 当前是“旧紫色深色主题 + 蓝灰新主题 + 浅色主题”的三套名称，但新主题通过替换旧 QSS 字符串生成，仍继承了旧主题的结构和部分视觉语义。
- 主题颜色同时以模块常量、`get_color()` 和大量页面内联 QSS 存在；这会造成切换主题后部分已构建页面不能即时更新，且硬编码 hover/语义颜色可能跨主题不一致。
- 全局 QSS 已覆盖大量 Qt 原生控件，但各页面仍大量重复设置局部 QSS；视觉系统存在全局规则与页面规则双轨维护的风险。
- 主窗口把主题选择、侧边工具栏、页面导航和较多业务交互聚集在 `main_window.py`，这是视觉重构的高冲突共享文件，应优先通过主题令牌和低侵入共享组件降低修改面。
- 主界面是“顶部视图工具栏 + 左侧操作栏 + 中央内容区 + 底部状态栏”的固定桌面工作台结构；页面容器通过显隐切换，而非真正的页面导航栈。
- 顶栏同时承担品牌、视图切换和下载进度，左栏同时承担主操作、导出配置、主题选择和辅助操作，信息架构偏工具堆叠，后续应把“当前工作区/主要动作/设置”分层。
- 默认主题仍是 `old`，主题选项仍显示“旧主题”；主题切换会弹出信息框提示视图需重启，说明主题状态更新体验目前不完整。
- 共享面板 `panels.py` 已有 `StatCard`、版本列表、资源包列表、版本详情、版本对比等可复用组件，但局部 QSS 仍使用导入时静态颜色常量，动态主题迁移需要统一令牌读取方式。
- 用户可见页面包括版本列表、图片预览、音频、角色图鉴，以及图片查看器、角色选择、导出设置等对话框；它们的视觉密度、按钮语义色和标题/工具栏模式存在重复但不完全一致的实现。
- 离屏基线截图（1440×900）显示：顶部栏、左侧栏和表格均有明显的细线框与深色块，但主内容下半区几乎完全空置；当前界面更像“控件集合”，缺少工作区标题、上下文摘要、空状态和层级引导。
- 蓝灰主题仍保留紫色品牌标题、蓝色选中态、绿色/蓝色/红色动作描边等多组强调色，色彩角色没有收敛；这是“AI 味”的主要来源之一，而不是蓝灰本身。
- 顶部视图导航和左侧操作区的控件高度、按钮密度、文字层级不统一；侧边栏在大窗口下留下大量无意义空白，主表格列宽也没有充分利用可视空间。
- 基线截图中的中文在离屏环境缺少匹配字体而显示为方框，不能据此判定真实用户环境的字体问题；但字体 fallback、字号和字重仍应纳入设计令牌与启动检查。
- 三个功能视图截图显示了共同模式：标题栏、控制栏、内容区、底部状态/播放栏分别用横向色带切开，边框线较多；空数据时主要呈现大片空白，缺少明确的说明、下一步动作和上下文摘要。
- 图片预览与音频页面在无数据时的空状态没有成为内容区主视觉；角色页面虽然有左右分栏，但空数据时仍留下大块无内容面板，信息反馈不够友好。
- 音频页的播放栏、预览页的进度条、角色页的搜索和 CSV 操作都使用独立局部风格，后续应收敛到共享的工具栏、按钮、输入框和状态组件。
- Emoji 与 Font Awesome 图标同时存在（如音乐、图片、关闭、播放），风格和字体依赖不一致；建议建立单一图标策略，优先使用 Qt/Font Awesome 图标并为无图标环境提供可读文字。
- 三主题对比截图确认：旧主题只是紫色强调色更重，结构问题没有变化；蓝灰主题是最合适的重构基线，但必须收敛品牌色、状态色和边框层级；浅色主题存在明显的混合渲染问题，部分中央内容仍使用深色局部 QSS，不能作为可交付主题。
- 主题切换的实现方式是全局 QSS 替换 + 页面创建时读取颜色常量，导致浅色主题与动态切换天然容易失配；这应作为视觉基础设施问题优先修复，而不是继续给每个页面补颜色。
- 新安装并审查了 `pyside6-fluent-ui`：它是针对 PySide6/Qt Widgets 的 Codex Skill，提供语义令牌、QPalette + 单一应用级 QSS、动态属性、控件状态、可访问性、工作台 Shell 和验证脚本，适合做 XL 的方法论参考。
- 该 Skill 明确要求保留 Qt 原生行为、不要迁移 QML/React、不要依赖散落的 `setStyleSheet()`、不要用 Emoji 作为正式图标、不要用卡片堆叠替代层级；这些原则与 XL 当前问题直接对应。
- Skill 自带静态校验已通过：60 个包校验、459 个主题令牌验证、PySide6 运行时可用；自带对比度检查的 light/dark/workbench 配置均通过。
- 不采用整个 Fluent 模板运行时或 `qfluentwidgets` 依赖；只将其令牌分层、状态矩阵、图标策略、QPalette/QSS 架构和验证清单翻译为 XL 自有实现，避免第三方依赖和外观同质化。
- 已创建 GitHub Issue #27《重构：XL 桌面界面视觉系统与蓝灰主题收口》，明确了第一阶段文件边界、非目标、保持行为和验收标准。
- 第一阶段离屏截图显示：紫色品牌已去除、主操作已收敛为蓝色语义按钮、主题入口只显示正式蓝灰主题；整体仍保留原版本表格的大面积空白和局部动作色，这是下一阶段页面信息架构/表格改造的明确边界。
- 用户已完成第一阶段正常启动验证：统一蓝灰界面、XL/资源工作台品牌、更新/导入/页面切换、单一主题入口和无重启提示均符合预期。
- 第二阶段审查确认三个功能页面重复实现页头、操作栏、关闭按钮、状态栏和局部按钮 QSS；已抽出 `app/ui/widgets/view_chrome.py`，用 Qt 原生控件和语义动态属性统一这些结构。
- 页面标题与操作按钮中的 emoji 已移除，避免 Emoji、Font Awesome 和系统字体混用造成的视觉不一致；保留现有 Font Awesome 导航图标作为统一图标策略的过渡。
- 版本列表新增“版本工作区”说明和摘要，摘要显示版本总数、已下载版本数和当前选择数；版本视图显隐由 `_set_version_content_visible()` 统一管理。
- 第二阶段离屏页面构建和截图通过；在当前沙箱中中文字体缺失，仅用于结构、色彩和控件状态检查，不能替代用户真实环境验证。
- 用户反馈验证发现图片预览空状态显示为底部整条黑色横条；根因是空状态 QLabel 被放在主 VBox 的末尾，而非图片区内容层。已改为内容区网格叠加，文字居中且透明背景；角色页同类布局一并修正。
- 用户实机截图进一步暴露角色页面板之间的纯黑间隙；源码确认页面根容器和内容容器是透明 QWidget，间隙显示 Qt 默认背景而非 XL 主题色。已通过应用级语义 QSS 统一为 `BG_DARK`，不删除有意义的布局间距。
- 角色截图还显示右侧详情面板在未选择时只有左上角单句提示，造成大面积无上下文空白。已将详情正文和空状态拆成同一详情面板内的叠加层：未选择时居中提示，选中后显示原有详情内容。
- 用户确认当前交互修正无问题，并提出角色详情需要 Wiki 化。源码审查确认 `build_character_detail_html()` 将基础信息、战斗属性、技能、消耗、语音和故事全部串成单段 HTML，再放入一个 QLabel；这解释了“信息完整但展示粗糙”的根因。
- 现有角色数据已经具备 Wiki 第一阶段所需的大部分字段：身份信息、初始/满级属性、技能文本、突破/升级消耗、语音和故事；不需要先改 Lua 解析器。
- 主窗口离屏构建在数据库初始化处被环境权限阻断：当前 `CodexSandboxOffline` 身份无法向项目 `logs/` 和 `data/` 写入，logger 可降级但 SQLite WAL 无法打开；用户已验证正常启动，因此不修改业务路径来迁就沙箱。

## Technical Decisions
| Decision | Rationale |
|----------|-----------|
| 先做跨页面视觉审计，再确定第一批改动 | 避免不同页面各自改色，最终形成新的视觉碎片化。 |
| 视觉层与业务层分离推进 | 尽量只改主题、共享组件和布局表现，不触碰解析、下载、导出等业务逻辑。 |
| 采用“设计令牌 + 页面分层 + 共享组件”路线 | 便于多人并行、减少共享文件冲突，也便于后续继续扩展主题。 |
| 不以“换一套颜色”作为完成标准 | 当前主要问题还包括视觉层级、控件一致性、重复局部 QSS、状态反馈和页面密度，单纯调色不能解决 AI 味。 |
| 蓝灰主题作为唯一主线，旧/浅色先降级处理 | 旧主题保留兼容映射可避免用户配置失效；浅色主题先隐藏或标记实验态，待全局令牌迁移完成后再决定是否恢复。 |
| 参考 PySide6 Fluent UI 方法，不直接复制 Fluent 外观 | XL 需要专业资源工具的识别度；借鉴的是桌面工程方法和状态规范，而不是把 XL 做成 Fluent/VS Code 克隆。 |
| 不引入新的 UI 运行时依赖 | 当前任务可用 PySide6、QSS、QPalette、QtAwesome 和现有资源完成；新增库会增加打包、许可证和多人环境同步成本。 |
| 第一阶段不重写版本表格 | 先验证主题基础和主窗口壳层，避免把信息架构、数据列和视觉基础绑成一个不可回滚的大改动。 |
| 第二阶段抽取 `view_chrome.py` | 先统一三个页面的重复视觉骨架，再分别处理内容密度和空状态；降低页面间差异与多人协作冲突。 |
| 版本摘要采用轻量文字层级 | 用工作区标题、说明和摘要解决“控件集合 + 大片空白”，不继续堆叠装饰性卡片。 |
| 空状态使用内容区叠加 | 让“暂无数据”成为内容区上下文水印，不占用底部空间，也不改变列表/详情主体尺寸。 |
| 页面间距使用 `BG_DARK` | 间距仍承担分组作用，但不能暴露平台默认黑色；统一根容器背景比逐个子面板补色更适合多人协作。 |
| 详情空状态使用叠加层 | 保持现有详情控件和渲染回调不变，仅切换可见性，让未选择/已选择状态有明确的视觉层级。 |
| 角色 Wiki 先做结构化展示模型 | 先把数据分组与 UI 组件解耦，再做美术层级；避免继续在一个 QLabel 的 HTML 字符串上堆样式。 |
| 角色资料采用渐进式 Wiki | 第一阶段复用已有字段并做好阅读体验；头像、关系图谱和复杂资源关联等高成本内容后置。 |
| 技能数字高亮作为详情页局部开关 | 不改变原始技能文本，默认保持正常阅读；需要核对倍率、百分比和持续时间时再一键开启。 |

## Issue #28 首版实现观察

- `app/core/character_profile.py` 将已有角色字典转换为纯 Python `CharacterProfile`，展示分组不依赖 Qt，也不改变 Lua、缓存和 CSV 契约。
- `app/ui/widgets/character_profile.py` 负责 Wiki 详情分区；`character_view.py` 只保留页面布局和控件出口，`main_window.py` 只负责选中角色后传递模型。
- 数字高亮使用转义后的富文本，仅作用于技能描述中的阿拉伯数字、百分比和小数；点击按钮即可开启/关闭，避免把数值标注耦合到解析器。
- 星落 Wiki 的参考价值主要是信息架构：身份、基础/成长属性、技能、语音、故事分层展示；XL 不直接复制其素材、页面代码或视觉皮肤。

## Issue #29 页面收口观察

- 音频页原先在输出目录不存在或为空时只显示空树，用户需要依赖底部状态栏理解下一步；内容区叠加空状态后，与图片和角色页的反馈模式一致。

## Issue #32 回归问题（2026-08-19）

- 角色页切换链路为 `角色按钮 → _start_lua_decrypt() → _load_character_data()`；应用每次启动时 `_character_data_loaded=False`，因此首次切换角色页就会重新解析。旧的 `output/lua` 平铺目录会返回 `version=None`，现有实现没有先读取 `characters_full.json`，所以日志表现为每次现场解析。
- “最新 Lua”判断错误地取了版本数据库中的最大时间戳，而不是 `output/lua/<版本>/` 中已经实际发布的最大目录。数据库中存在但尚未导出的版本不应参与自动角色解析判断。
- 旧缓存路径没有迁移进角色仓库；同版本重导或从旧缓存首次迁移时缺少稳定基线，导致整批角色被标为“新”。
- 未读状态目前只绘制在角色表格，顶部四个视图按钮没有共享未读状态，也没有一键清除入口。
- `_import_selected()` 原本把版本全部已下载 AB 放入 AssetStudio 输入目录；即使只勾选 Lua，CLI 仍扫描整个目录。当前 `data/bundles/134309118097910091/_map/assets_map.json` 可将 Lua 资源精确映射到 2 个 bundle，因此需要在 CLI 侧使用只含命中包的临时输入目录。
- 导入完成处理器先关闭进度弹窗，再触发 Lua 自动角色解析，自动解析阶段无法复用用户已经看到的进度窗口。

### 启动回归补充

- 顶部导航加入未读角标时，导航构建函数将 list/image 等名称字符串直接传给 _tbtn(icon=...)；当 QtAwesome 可用时，setIcon(str) 立即触发 PySide6 类型错误，导致整个主窗口无法启动。
- 修复方式为在导航构建层统一调用 _icon()，让 _tbtn() 始终只接收 QIcon 或 None；新增 Qt 工具栏构建 smoke，避免再次把图标名称和图标对象混用。
- 用户实机反馈角色未读红点错误出现在所有顶层标签；根因是角色未读集合被无差别同步到四个导航角标。已收窄为仅“角色”标签显示，其他标签等待各自建立独立未读来源后再接入。
- 音频列表刷新前未显式重置 `_audio_file_items`，在目录被删除或扫描失败后存在旧叶节点仍可被导出的风险；本轮在加载入口重置，未改变扫描和导出逻辑。
- 预览列表已经支持多选和批量右键操作，但状态栏只显示总数；新增选择数反馈，不改变选择模型和导出流程。
- 预览、音频、版本页原本分别维护局部 QSS；本轮将稳定的控件样式迁入 `theme.py`，页面只保留对象名和行为，降低主题分叉和多人协作冲突。

## Issue #30 对话框收口观察

- 图片查看器、角色选择、导出设置都能正常工作，但各自通过 `setStyleSheet()` 固定颜色，无法充分复用正式主题；对象名 + 全局 QSS 更适合长期维护。
- 图片查看器在空路径列表时只更新 `0 / 0`，上一张/下一张按钮仍保持可用；这属于小状态缺口，本轮补为明确禁用，不改变导航逻辑。
- 角色选择对话框空列表时滚动区域没有上下文提示；增加“暂无可导出的角色”，不影响 `selected_roles()` 返回集合契约。
- 右键菜单动作文本中的 emoji 依赖字体且与页面正式风格不一致；只改显示文本和样式归属，不修改 QAction 分支判断。

## Issue #32 Lua/角色数据链路审查（2026-08-19）

- 当前版本选择使用数据库中的 `timestamp`，版本列表通过 `ticks_to_date()` 展示日期；它可以作为 Lua 版本目录的稳定主键，目录建议使用 `output/lua/<timestamp>/`，同时保留日期/版本信息在元数据中，避免同一天多个版本互相覆盖。
- `ImportASWorker._stage_export()` 先把分类导出到 staging，再通过 `_commit_staged_material()` 提交到 `data/material`；Lua 反编译发生在 staging 内，当前提交后 `_sync_lua_output()` 将 Lua 合并覆盖到单一 `output/lua`。
- Lua 版本化应放在 staging 提交成功之后：先复制到 `output/lua/<version>`，验证必要文件，再清理 `data/material/assets/lua`；复制失败或自动解析失败不能回滚已经成功的 Lua 最终产物，也不能删除历史版本。
- 角色解析当前由 `MainWindow._load_character_data()` 协调，使用单一 `output/character_data/characters_full.json` 和源文件 mtime 缓存；该格式无法表达版本历史、字段变化和未读状态，需要升级为带版本快照、当前合并数据和 pending 变化记录的持久化仓库。
- `load_character_data(lua_dir)` 是无 Qt 的纯解析入口，已经支持 BaseCard/BaseWord/BaseSkill 等文件组合；`BaseCard.lua`、`BaseWord_cn.lua` 和相关 Base 文件缺失时应明确返回不可自动解析，而不是写入空数据覆盖旧结果。
- 自动角色解析的触发条件必须由版本元数据决定，而不是仅检查 `output/lua` 是否存在：本次导出的版本必须是版本列表中的最新版本，并且该版本目录满足角色解析所需 Base 文件集合。
- 角色列表目前由 `derive_character_index()` 从完整字典派生；新增/变更状态可在索引项中增加 `change_status`/`unread`，不改变角色详情模型和 CSV 导出字段，界面显示角标与清除状态应由 UI 协调层处理。
- 角色选中后 `_on_character_select()` 能拿到 `char_id` 并更新 Wiki 详情，是清除对应未读状态的稳定交互边界；刷新和重新加载时应继续保留未查看记录。
- `data/material` 仍被立绘预览、音频解密和 Spine 流程使用，本轮不能整体删除；仅 Lua 子目录可以在成功导出并完成最终复制后清理。
- 导出线程提交顺序为 staging → `data/material` 分类提交 → Lua 最终发布 → Lua 临时目录清理；历史 `output/lua/<版本>` 目录只会在同版本重复导出时替换，其他版本不受影响。
- Lua 发布只复制 `.lua`，不会把 `.lua.bytes`、`.lua.bank` 等反编译中间文件带入最终目录；没有生成 `.lua` 时不会替换已有版本目录，但仍清理本次临时目录。
- 自动解析由 `MainWindow._auto_parse_after_lua_export()` 触发，版本判断使用版本数据库中最大 timestamp；导出旧版本即使 Base 齐全也只留存，不更新当前角色仓库。
- 角色解析异常或返回空结果时，解析前不再清空内存中的旧角色数据，磁盘上的当前仓库和历史快照也不会被覆盖。
- 角色仓库的“增量”语义是：每个版本保存完整快照，当前索引更新为最新有效快照，新增/变更 ID 进入累积未读集合；打开详情只清除对应 ID，不影响其他未读角色。

## Technical Decisions（Issue #32）

| Decision | Rationale |
|---|---|
| Lua 最终文件按版本目录留存 | 版本可追溯，避免多版本导出相互覆盖；目录主键使用数据库 timestamp，适合与 ab 包对应。 |
| 自动解析只认“最新版本 + 必要 Base 文件” | 避免导出旧版本时误更新当前角色数据，也避免缺失 Base 文件写出不完整快照。 |
| 角色数据采用历史快照 + 当前合并索引 + 未读变化 | 同时满足保留历史、增量更新、查看差异和 UI 红点，不再用单一缓存覆盖过去。 |
| 先保留手动解析按钮 | 自动链路失败或用户需要补偿时仍有可操作入口；手动入口默认指向最新可解析版本。 |
| 只清理 Lua 临时目录 | `material` 还承担音频/立绘/FGUI 处理中间态，整体清理属于后续批次。 |
